2. Session Creation & Booking Flow

CRITICAL CORRECTION: Admin does NOT create sessions. System uses automated booking with sequential rules.
graph TD A[User Completes Pre-Assessment] --> B[AI Processing 48-72hr] B --> C[Processing Complete] C --> D[User Views Available Calendar Slots] D --> E{User Selects Time Slot} E --> F[System Checks Sequential Rule] F --> G{Existing Session on Calendar?} G -->|Yes| H[Block Booking] H --> I[Show Error: Complete Current Session First] G -->|No| J[Check Lead Time Rule] J --> K{48-72hr Lead Time Met?} K -->|No| L[Block Booking] L --> M[Show Error: Insufficient Lead Time] K -->|Yes| N[Temporarily Hold Slot] N --> O[Create Unique Meeting URL] O --> P[Send Confirmation to User & Liz] P --> Q[Slot Locked for All Other Users] style F fill:#ffc107,stroke:#856404,stroke-width:3px style J fill:#ffc107,stroke:#856404,stroke-width:3px style N fill:#28a745,stroke:#1e7e34,stroke-width:2px style Q fill:#28a745,stroke:#1e7e34,stroke-width:2px

Sequential Booking Rules (MANDATORY):

  • Rule 1: Users cannot book multiple sessions if one is already confirmed on calendar
  • Rule 2: 48-72 hour minimum lead time required for AI synthesis
  • Rule 3: Once slot is claimed (even if unconfirmed), unavailable to others (like plane tickets)
  • Rule 4: Unique URL generated per booking prevents duplicate sessions

Calendar Integration Requirements:

  • Research Calendly alternative that supports custom booking logic
  • Must support sequential session prevention
  • Must support minimum lead time enforcement
  • Must support temporary slot holding during booking process
  • DELETE: All admin session creation logic

48-Hour Execution Pattern:

  • Pre-Work: User completes pre-assessment questions
  • AI Processing: 48-72 hour synthesis period
  • Live Session: Facilitated conversation
  • AI Generation: Post-session deliverable creation
  • Validation: User reviews and approves
  • Deliverables: Final artifacts provided

4. System Architecture: Missions → Journeys → Quests → Sparks

graph TD A[SweetBOS Platform] --> B[22 Domains] A --> C[22 Tenets] A --> D[Universal L1-L5 Maturity Model] E[User Enters System] --> F[Selects Mission ~5-8 total] F --> G[Mission Contains Multiple Journeys] G --> H[Each Journey Contains Quests] H --> I[Each Quest Contains Sparks] I --> J[Spark = Execution Screen] J --> K[User Completes Spark Action] K --> L{Quest Progress} L --> M[Complete Quest] M --> N{Journey Progress} N --> O[Complete Journey] O --> P{Mission Progress} P --> Q[Analytics & Story Trail Updated] Q --> R[KPIs Tracked Per Quest] R --> S[Achievements Logged] S --> T[User Reflects on Progress] style F fill:#005A9C,stroke:#003d6b,stroke-width:3px style G fill:#00AEEF,stroke:#0086b3,stroke-width:2px style H fill:#7B2D8E,stroke:#5a1f69,stroke-width:2px style I fill:#ffc107,stroke:#856404,stroke-width:2px style Q fill:#28a745,stroke:#1e7e34,stroke-width:2px

Hierarchy Definitions:

  • Mission: Bundle of journeys (like a $100 bill)
  • Journey: Bundle of quests (collections for level transitions)
  • Quest: Bundle of sparks (3-10 minute atomic actions)
  • Spark: Single execution screen - what user DOES on their screen

Key Principles:

  • Users never "complete all missions" - continuous improvement model
  • System increases user's benchmark and standards over time
  • Quests interconnect across journeys (needs flowchart mapping)
  • Everything maps to 22 Domains and 22 Tenets
  • Universal L1-L5 maturity tracking across all domains

5. FAQ Builder Journey Flow (Intelligent Parsing)

CRITICAL REQUIREMENT: System must intelligently parse pasted Q&A content, not require manual separation.
graph TD A[User Enters FAQ Journey] --> B{Input Method?} B -->|Manual Entry| C[User Types Single Q&A Pair] C --> D[System Captures Question] D --> E[System Captures Answer] B -->|Bulk Paste| F[User Pastes Multiple Q&As] F --> G[AI Parses Content] G --> H[AI Detects Question Patterns] H --> I[AI Detects Answer Patterns] I --> J[AI Separates Q&A Pairs] J --> K[System Presents Parsed Pairs] K --> L[User Validates Each Pair] L --> M{Corrections Needed?} M -->|Yes| N[User Edits Specific Pairs] N --> L B -->|PDF Upload| O[User Uploads PDF] O --> P[System Extracts Text] P --> G B -->|Audio Input| Q[User Speaks Q&A] Q --> R[Speech-to-Text Processing] R --> G M -->|No| S[All Pairs Validated] S --> T[FAQ Collection Complete] T --> U[Generate Artifacts] U --> V[User Downloads or Adds to Google Drive] style F fill:#ffc107,stroke:#856404,stroke-width:3px style G fill:#7B2D8E,stroke:#5a1f69,stroke-width:3px style K fill:#00AEEF,stroke:#005A9C,stroke-width:2px style V fill:#28a745,stroke:#1e7e34,stroke-width:2px

Parsing Logic Requirements:

  • Pattern Recognition: AI identifies question vs answer structures
  • Multi-Format Support: Text paste, PDF upload, audio input
  • Validation Layer: Users review and correct AI parsing
  • Confidence Threshold: Re-ask if AI confidence is uncertain
  • Framework Enhancement: Use OCDA framework to enrich extracted Q&As

User Experience Principles:

  • Advisors have limited time - reduce friction
  • They likely have existing Q&A documents - enable bulk import
  • Don't force manual separation of questions and answers
  • Allow validation but don't require recreation from scratch

6. Spark Presentation Logic

Concept: Sparks adapt their presentation based on cognitive function and stage. Not all sparks are simple questions.

graph TD A[System Determines Spark Need] --> B{What's the Cognitive Function?} B -->|Information Gathering| C{Best Presentation?} C -->|Simple Data| D[Form with Input Fields] C -->|Complex Data| E[Table/Grid Entry] C -->|Multiple Choice| F[Radio Buttons / Dropdowns] C -->|Multi-Select| G[Checkboxes] C -->|Range Selection| H[Sliders] B -->|Information Delivery| I{Best Presentation?} I -->|Overview| J[Infographic Display] I -->|Detailed| K[Text Paragraphs] I -->|Comparison| L[Table Display] I -->|Process| M[Visual Diagram] B -->|Validation/Review| N{Best Presentation?} N -->|Simple Confirm| O[Yes/No Buttons] N -->|Content Review| P[Side-by-Side Comparison] N -->|Multi-Item| Q[Checklist with Approve/Reject] D --> R[Reduce Cognitive Load] E --> R F --> R G --> R H --> R J --> R K --> R L --> R M --> R O --> R P --> R Q --> R R --> S[Provide Focused Context to AI] S --> T[Minimize Context Window Bloat] style B fill:#7B2D8E,stroke:#5a1f69,stroke-width:3px style R fill:#00AEEF,stroke:#005A9C,stroke-width:2px style S fill:#28a745,stroke:#1e7e34,stroke-width:2px

Co-Evolution Framework Integration:

  • Explore Stage: Present all possibilities, open-ended inputs
  • Attune Stage: Filter to relevant options based on context
  • Decide Stage: Force selection from viable choices
  • Execute Stage: Action-oriented inputs with clear outcomes

Design Principles:

  • Every screen interaction should feel like consistent "spark" experience
  • Pre-assessment should use same spark presentation patterns
  • Maximum 5 questions per screen to avoid scrolling
  • Form elements must be functional, not decorative
  • Progress indicators should be clickable for navigation
